# Legacy encodings, missing glyphs, and hashing only what moved — 2026-08-23

Three owner rulings, taken in the order they were given, because the first is
the one that decides whether a book opens at all.

1. Sweep item **#52** — an EPUB whose XHTML declares a legacy encoding could not
   be parsed. Now it can, for 29 single-byte code pages, and what still cannot
   fails loudly with a Book Note naming the encoding.
2. Sweep item **#38** — "a character the reading font lacks renders as empty
   space." **It does not, and has not since B-009.** What it actually does is
   worse, and that is what was fixed.
3. Update Library SHA-256'd every book on every run. It now hashes only a book
   whose size or modification time has moved.

`SECTION_FILE_VERSION` 45 → **46** ([Section.cpp](../lib/Epub/Epub/Section.cpp)).
`notes.bin` version 1 → **2** ([BookNotes.cpp](../lib/Epub/Epub/BookNotes.cpp)).
A new file, `/.crosspoint/library_sync.json`, at version 1.

| | Before | After |
|---|---|---|
| `pio run -e simulator_x3` | SUCCESS | SUCCESS |
| `pio run -e gh_release` | SUCCESS, flash 4,971,779 (75.9%), RAM 54,276 (16.6%) | SUCCESS, flash **4,987,371 (76.1%)**, RAM **54,556 (16.6%)** |
| Host tests | 411/413 | **447/449** |

Flash **+15,592 B**: 7,424 B of code-page tables, ~1,600 B of alias rows and

## 1. Legacy encodings (sweep item #52)

### Reproduced first

`tools/make_encoding_book.py` writes a five-chapter fixture whose chapters are
RAW BYTES in the encoding each one declares — UTF-8, windows-1252, ISO-8859-1,
windows-1251 and Shift_JIS. Writing UTF-8 under a lying declaration would not
have exercised the bug, which is in the decode.

Opened on `simulator_x3` before any change, paging forward from chapter 0:

```
[3084] [ERR] [EHP] Parse error at line 1:
unknown encoding
[3084] [ERR] [SCT] Parse error during incremental build
[3084] [ERR] [ERS] Failed during incremental section build
```

and then that same three-line block again for every further press of
page-forward. **The reader is not merely missing a chapter; it is stuck.**
Page-forward retries the failing chapter for as long as anyone keeps pressing,
which is what "cannot be opened" looks like from the outside.

### What expat actually builds in, and what it wants

Four encodings: UTF-8, UTF-16, US-ASCII and ISO-8859-1. Everything else is
`XML_ERROR_UNKNOWN_ENCODING` unless the host installs an
`XML_SetUnknownEncodingHandler`, and there was none anywhere in this repo. The
handler is handed the declared name and fills a 256-entry map of Unicode
scalars; a negative entry declares a multi-byte lead and obliges a `convert`
callback.

`XmlInitUnknownEncoding` ([xmltok.c](../lib/expat/xmltok.c)) refuses a table
outright — no handler at all, indistinguishable from having none — if a byte
below 0x80 is not the identity for any byte it classifies, or if any entry is
outside the BMP. Both constraints are enforced by the generator, and asserted
again against the shipped file in `test/xml_encodings`, because the `.cpp` can
be edited without going through the generator.

### The set chosen, and why that set

**29 single-byte code pages**, generated by
[tools/gen_xml_encodings.py](../tools/gen_xml_encodings.py) into
[lib/Epub/Epub/parsers/XmlEncodingTables.cpp](../lib/Epub/Epub/parsers/XmlEncodingTables.cpp)
from Python's own codec tables — the nine Windows pages, windows-874, the
fifteen ISO-8859 parts, KOI8-R and KOI8-U, and four Mac pages. 85 aliases, all
matched after normalisation (lowercased, punctuation dropped), so
`Windows-1252`, `windows_1252` and `CP1252` are one row.

**7,424 bytes of table.** Choosing among these would have cost more argument
than it saved: the marginal code page is 256 bytes against 1.5 MB of free flash,
and leaving one out means a book that will not open for a reason nobody can
guess from the outside.

**No multi-byte encodings.** Shift_JIS, EUC-JP, Big5, GB2312/GBK/GB18030,
EUC-KR and the ISO-2022 family are refused, and the reason is not only that
their tables are 14–44 KB each:

* This firmware carries **no CJK reading face**. The only built-in reading
  family is Libre Franklin ([fontIds.h](../src/fontIds.h)); CJK coverage exists
  only if the reader has installed a `.cpfont` that carries it. Spending 44 KB
  to decode GBK into a page of replacement marks buys nothing.
* The convert-function path is per character and reads a table on every
  multi-byte sequence, which is a different performance shape from a 128-entry
  lookup.
* The refusal is now *loud*, which the whole-class failure was not.

A CJK library is a real thing to want, and the way to have it is a table plus a
CJK card font, together. It is not a cheaper subset of this.

### Installed on every parser, not only the chapters'

[XmlEncodingSupport.h](../lib/Epub/Epub/parsers/XmlEncodingSupport.h) /
[.cpp](../lib/Epub/Epub/parsers/XmlEncodingSupport.cpp), called immediately after
`XML_ParserCreate` at all five sites: `ContainerParser:17`,
`ContentOpfParser:48`, `TocNavParser:20`, `TocNcxParser:20`,
`ChapterHtmlSlimParser:2333`. An EPUB is free to write its OPF in one encoding
and its chapters in another, and the OPF/TOC half of the failure used to be
log-only.

**Undefined bytes decode to U+FFFD, not to expat's "illegal byte" (-1).** Five
positions in windows-1252 are undefined; mapping them to -1 would fail the whole
chapter over one stray byte, which is the outcome this feature exists to remove.

### The note

`booknotes::Note::TextEncodingUnsupported`, **book scope**, carrying the
declared name in a new 24-byte `Details::unsupportedEncoding`. The first name
seen wins: a book is written in one encoding in practice, and the reader has
already stopped at the first.

Storing a NAME rather than an id is the point — there is no enumeration of the
encodings that do not exist here, and saying which one is the whole content of
the note. That is what took `notes.bin` to version 2; a v1 file is discarded
whole, which costs one re-parse of a book already on the card.

### Proved by rendering

`fs_/books/encodings.epub`, `simulator_x3`, grain off, palette forced to
black-on-white. Landing confirmed from `[ACT] Entering activity:` and
`[XEN] Decoding as ...`, not from the pictures.

```
[2586] [DBG] [XEN] Decoding as 'windows-1252'
[5591] [DBG] [XEN] Decoding as 'windows-1251'
[6583] [ERR] [XEN] No table for declared encoding 'shift_jis'; this chapter cannot be decoded
```

`cp1252_punctuation_crop_3x_nearest.png` is the evidence figure: the
0x80–0x9F band arriving as curly quotes, an em dash and an ellipsis, which is
exactly what separates windows-1252 from ISO-8859-1 and the only place a build
quietly serving latin-1 would show it. `enc_notes.png` is the Book Notes screen
naming `shift_jis`.

### What is still not handled, deliberately

A file whose bytes are windows-1252 and which **declares nothing** is assumed to
be UTF-8 by expat and fails on the first high byte. That is a different repair —
sniffing, not decoding — and it is not this one.

## 2. Missing glyphs (sweep item #38)

### The sweep item is wrong, and reproducing it is what showed that

The entry reads: *"A codepoint the reading face lacks draws NOTHING — no
`.notdef`."* It has not been true since **B-009**.
`EpdFont::getGlyph` ([EpdFont.cpp](../lib/EpdFont/EpdFont.cpp)) already
substitutes, in order: U+FFFD if the face carries one, else `'?'`. A face
carrying neither returns nullptr and draws nothing — that is the residue the
sweep saw, and for a *text* reading face it never happens, because every text
face has a question mark.

A fixture with a snowman, a Han character, a Hangul syllable and an emoji
between ordinary words, rendered two ways:

| Reading face | What a reader sees today |
|---|---|
| LibrisADF from the card (the shipped default) | U+FFFD — the black diamond. Unmistakable. |
| Libre Franklin, the only BUILT-IN reading family | a plain **`?`** |

`glyphs_question_before_crop_3x_nearest.png` is that second case at native
pixels. **A `?` standing in for a missing character is worse than empty space**,
because it reads as a question mark the author typed. Nothing on screen and
nothing in the logs distinguishes the two.

So the defect that remains is not "nothing is drawn". It is: the honest case is
invisible to the reader, and nobody is ever told.

### The seam, established before designing

The sweep said the fix was blocked because detection lives in `GfxRenderer`,
which every UI screen also draws through, so raising a BOOK note from it needs a
seam that does not exist. That is true of `GfxRenderer`. It is not true one
level down. There are exactly **two** places where this firmware decides "this
face cannot draw that", and both are in `lib/EpdFont`:

1. `EpdFont::getGlyph`'s last-resort branch — every built-in face, and every SD
   face for a codepoint the advance table has not already answered for.
2. `SdCardFont::buildAdvanceTable` — an SD reading font substitutes the
   replacement glyph's ADVANCE for a missing codepoint, so `getTextAdvanceX`
   finds a cached advance and **never reaches `getGlyph` at all**. Missing this
   one is why the first version of the ledger read zero for every book on a
   shipped card; it was caught by rendering, not by review.

### What was built, and what was rejected

**Rejected: extend the fallback chain to reading fonts.** Not on taste — on
measurement. `setFallbackFont` exists and is used, but `resolveTextFontId`
([GfxRenderer.cpp:188](../lib/GfxRenderer/GfxRenderer.cpp)) redirects the
**whole string**, and only for CJK. The only built-in coverage face is Noto Sans
at **8, 10 and 12 pt** ([main.cpp:457](../src/main.cpp)), while reading sizes run
to 24. One missing character would set an entire line in a face less than half
the size of the text around it. `SdCardFontSystem::setupUiFallbacks`
([SdCardFontSystem.cpp:159](../src/SdCardFontSystem.cpp)) already runs this
chain in the other direction — UI font falling back to the SD reading font — and
there is no reading-size coverage face to point the other way at.

**Built: a visible `.notdef` box, and a note counting the characters.** Both,
because they answer different questions: the box says *here*, the note says *how
many and why*.

The box is drawn only where the substitute was the `'?'` last resort. A face
that carries U+FFFD already draws an unmistakable mark and is left alone.

**The metrics trick is the whole implementation.** The box is painted into the
substitute glyph's own cell — its width, height, left and top — so every measure
walk in `GfxRenderer` has already measured exactly the box that will be drawn.
No invented advance, nothing to keep in step. That is B-036's lesson taken from
the other side: the measured page and the drawn page differed there because a
hole was handled differently in two walks, and the cheapest way not to repeat it
is to have only one set of numbers. Rendered before and after are line-for-line
identical outside the glyph cells: diff bbox (9,149)–(512,559), 1.501% of pixels
changed by more than 4 levels, and the line breaks do not move.

`EpdFont::getGlyph` gained an optional `GlyphSource*` out-parameter. Defaulted,
so all ~15 existing call sites are untouched: a caller that only wants metrics
does not care which glyph it got, and by construction the metrics are the same.

**The ledger** is [lib/EpdFont/MissingGlyphLedger.h](../lib/EpdFont/MissingGlyphLedger.h)
— a file-scope singleton counting **distinct** codepoints in a 64-slot
open-addressed table (256 B of DRAM). Distinct, not occurrences: a page
repaints, and an occurrence count would climb every time the reader turned back
to it. Full means the count stops and says so (`isSaturated`), which is why the
note reads "**at least** %u".

It is **armed** and disarmed by default. `ChapterHtmlSlimParser::beginParse`
arms it; both endings of a parse disarm and report. Every UI screen draws
through the same renderer, and a filename or a model's answer carrying an emoji
is not a fact about the book. Its lifetime is owned by `booknotes::Notes`
(`clear()` and `setLayoutFingerprint()` both reset it), so there is one place
that can get it wrong rather than three.

`booknotes::Note::MissingGlyphs` is **layout scope** — a different reading font
has a different set of holes, and a count quoted about a face the reader has
since changed is a lie with a number in it.

### One deliberate behaviour change beyond the book

A UI screen drawing a codepoint its face lacks now shows a box where it showed
`?`. Libre Franklin carries no U+FFFD, so this reaches filenames, note titles
and model answers as well as book text. It is the same argument: a `?` that is
not a question mark is a lie, and a box is not.

### Two things the ledger does not see, stated

* A codepoint whose advance was cached while the ledger was disarmed — a
  filename on Home, say — is never counted when it later appears in the book.
* Layout-scope notes are incomplete by construction; they know only about the
  chapters paginated so far. That is unchanged from the 2026-08-23 design.

### The scope predicate changed, and it had to

`isLayoutScope` was `n >= FIRST_LAYOUT_NOTE`. Under that rule a **book-scope**
note appended to the end of the enum becomes layout-scope silently — a note that
deletes itself the first time the reader changes font. The enum must stay
append-only because its values are persisted, so the ordering test had to go: it
is now an explicit `switch`, and every new note names its own scope.
`test/book_notes` walks the whole enum against the predicate rather than against
a boundary value, so a note added tomorrow is covered the day it is added.

## 3. Update Library: hash only when size or mtime moved

### What it did

`syncBook` asked `sizeVerdict`, and on CHECK_SHA read the entire book off the
card and SHA-256'd it — every book, every run, to learn almost always that
nothing had changed ([LibraryUpdater.cpp](../src/network/LibraryUpdater.cpp)).

### The ledger

`/.crosspoint/library_sync.json`, **version 1**, one record per book: filename,
size, FAT modification date and time, and the digest that was verified.

`librarysync::hashVerdict` ([LibrarySyncPlan.h](../src/network/LibrarySyncPlan.h))
is pure and host-tested. It answers SKIP_HASH only when *all* of: a record
exists, the HAL gave a modification time, the size matches the record, the date
and time both match the record, and the manifest still asks for the digest the
record carries. **Every way of not knowing is MUST_HASH**, and that is the whole
safety argument — the first run after this shipped has no records at all, and a
verdict that skipped on a missing record would declare the entire library
unchanged forever, which looks exactly like a very fast, very successful sync.

The stored digest is never used to decide a DOWNLOAD. A manifest asking for
different bytes at the same size forces a real read; the record is evidence, not
permission.

Written once at the end of a run (`flushSyncRecords`, called from
[LibraryUpdateActivity::runSync](../src/activities/settings/LibraryUpdateActivity.cpp)),
not per book: the first run touches every entry and a rewrite each time would be
O(books²) card writes to save a hash that run is already paying for. A run that
dies before the flush costs the next run one more hashing pass, which is exactly
the old behaviour.

### The manifest had no versioning at all

Checked: `fetchManifest` read `doc["books"]` and nothing else. It now reads
`doc["version"] | 1` — an unversioned file is version 1 by definition, so
nothing published today changes — and refuses anything higher with a new
`MANIFEST_TOO_NEW` error and its own sentence on screen. A future manifest that
redefines `bytes` or `sha256` would otherwise be acted on silently, and the
damage is downloads over books that were fine.

### Measured

Headless on `simulator_x3` against `CROSSPOINT_SIM_HTTP_MOCK_ROOT` serving a
release JSON, a manifest and the book bytes; Wi-Fi joined through
Settings → Wi-Fi Networks first, and both syncs run in ONE process so one
connection serves both. 27 books, **18,133,982 bytes** on the card, every one of
them unchanged.

| | Run 1 (no ledger) | Run 2 (ledger present) |
|---|---|---|
| Book bytes read from the card | **18,133,982** | **0** |
| Wall clock, first book to last | 125 ms | 104 ms |

**The wall clock is the weaker of the two figures and is reported as such.** The
host hashes with CommonCrypto over a warm page cache, and 27 per-book progress
repaints (~4 ms each) dominate the loop either way. The figure that transfers to
the device is the one above it: 18 MB read through SdFat's single shared
512-byte sector cache, or none. The device figure itself is **unmeasured** —
there is no paired device here.

Correctness was checked in the same harness, not inferred:

* first run, no ledger — `No sync ledger yet; every book will be hashed once`,
  27 books hashed, ledger written;
* second run — 27 × `Unchanged (size and mtime match the ledger, not read)`;
* **one byte flipped in the middle of a book, size unchanged** — the case a
  size-only skip would miss. Caught (the mtime moved), re-hashed, digest
  mismatched, downloaded: `library sync done: 1 updated, 26 unchanged, 0 errors`.
  The following run skipped it again.

A card written by a device with no clock stamps every file 0/0. That is a real,
comparable value and the plan treats it as one; treating it as "unknown" would
mean the skip never fires on exactly the devices this was for.

## Notes for whoever drives this headlessly next

* **Confirm inside the reader opens Select Chapter.** The simulator's
  `CLAUDE.md` says "Inside the reader Confirm does nothing — there is no reader
  menu"; the second half is right and the first is not
  ([EpubReaderActivity.cpp:458](../src/activities/reader/EpubReaderActivity.cpp)).
* Select Chapter opens with the CURRENT chapter selected, not row 0, so reaching
  the `Book Notes (N)` row means walking LEFT as many times as you paged.
* Home's menu row indices depend on how many recent-book covers are showing.
  Over-shoot with RIGHT until the selection clamps on Settings, then count LEFT.
  The 2026-08-21 order below Settings is: Update Library, Update Firmware,
  Claude, Create Note, File Transfer, Manage Files, Browse Files, Recent Books.
* File Transfer is not a way to leave Wi-Fi connected for a later screen: its
  `onExit` disconnects and calls `silentRestart()`. Settings → Wi-Fi Networks
  is, because `WifiSelectionActivity::onExit` deliberately does not disconnect.
