# Indexing performance, 2026-08-23

Owner report, verbatim: *"indexing on x3 is taking a lot of time. fond
optimizations for that and other laggy areas"*.

Measured first, then changed. Three fixes landed; every one of them leaves the
section cache **byte-identical**, so no `SECTION_FILE_VERSION` bump and no
pagination change. Everything found and not changed is listed at the end with
its measurement, so the next session does not pay for the same survey.

## What "indexing" turned out to be

Two different operations show the same `Indexing` popup and only one of them is
slow.

| | Where | Cost (host, `-O2`) |
|---|---|---|
| **Book index** — spine + TOC + CSS into `book.bin` | `lib/Epub/Epub.cpp:488`-`:560`, popup at `src/activities/reader/ReaderActivity.cpp:60` | **4 ms** for a 24-chapter book |
| **Section pagination** — one spine item laid out into `sections/N.bin` | `Section::startBuild` / `buildSomeMore` (`lib/Epub/Epub/Section.cpp:308`, `:494`), popup at `EpubReaderActivity.cpp:1096` and `:1277` | **all of it** |

So "indexing" means pagination. The book index is 1.6% of a cold open and is
not worth touching — that is the first negative result, and it is the one that
would otherwise have been optimized first.

Pagination is **per spine item, lazily**. A book is never indexed as a whole:
the reader lays out 8 pages, shows one, and the background tick follows the
reader (`EpubReaderActivity.cpp:338`, `BUILD_WINDOW_AHEAD`). The waits the owner
sees are therefore the ones that must reach a *specific* page before drawing:

* a resume deep into a chapter,
* crossing a suspended partial's watermark, which re-lays the chapter out from
  page 0 (`Section::startBuild` always re-parses from byte 0 — `Section.cpp:343`),
* a percent jump, which needs the final page count (`EpubReaderActivity.cpp:1094`).

## Method

Desktop simulator, `simulator_x3` (X3 profile, 792x528 framebuffer, LibrisADF
18 pt, the shipped default). A cold section build is forced by writing
`progress.bin` with a deep target page and deleting `sections/`.

Corpus, generated by `tools/make_perf_book.py` (deterministic, real dictionary
words so hyphenation and kerning are not measuring a lorem block):

| Book | Shape | Pages |
|---|---|---|
| `measure.epub` | 24 chapters, 2.64 MB XHTML, 110 KB per chapter | 246 per chapter |
| `giant.epub` | 1 chapter, 2.56 MB XHTML — the giant-single-spine case the code comments call out | 5,816 |

```bash
python3 tools/make_perf_book.py fs_/books/measure.epub 24 120
python3 tools/make_perf_book.py fs_/books/giant.epub 1 2800
# force a cold build of spine 0 and resume past its end
python3 - <<'PY'
import struct
open('fs_/.crosspoint/epub_<hash>/progress.bin','wb').write(struct.pack('<HH', 0, 60000))
PY
rm -rf fs_/.crosspoint/epub_<hash>/sections
SDL_VIDEODRIVER=dummy CROSSPOINT_SIM_INPUT_SCRIPT='20000:QUIT' .pio/build/simulator_x3/program
```

**Two things about the host that will mislead you if you skip them.**

1. **PlatformIO's native env passes no `-O` flag at all**, so a plain
   `pio run -e simulator_x3` is `-O0` and ~1.5x slower than the device build's
   optimization level. Every number in this document is from
   `PLATFORMIO_BUILD_FLAGS="-O2 -g" pio run -e simulator_x3`.
2. **The host's `HalFile::write` is a POSIX `write()` syscall; the device's is
   SdFat into a 512-byte sector cache.** The host therefore over-weights write
   cost in wall-clock terms. What transfers exactly is the *call count*, which
   is why the instrumentation added below counts calls, not bytes.

Timing comes from the existing `LOG_DBG` idiom
(`[EHP] Time to parse and build pages`, `ChapterHtmlSlimParser.cpp:2388`) plus
the one line added here; the call graph comes from macOS `sample` at 1 ms,
aggregated to self-time per symbol.

## The breakdown, before any change

`giant.epub`, one 5,816-page spine, `-O2`. Build thread, 3,826 samples:

| Phase | Self samples | % of build thread | Runs |
|---|---|---|---|
| `Page::serialize` → `HalFile::write` | 3,252 | **85.0%** | 398 calls per page |
| render task idle (`cvwait`) | 320 | 8.4 | — |
| `SdCardFont::getMeasureKern` | 85 | 2.2 | per adjacent character pair |
| `SdCardFont::buildAdvanceTableRange` | 24 | 0.6 | per text block |
| `_platform_strcmp` (expat / tag dispatch) | 43 | 1.1 | per element |
| `utf8NextCodepoint`, `addWord`, hyphenation, everything else | < 60 | < 1.6 | |

Wall clock for the same run: zip inflate of the spine 22 ms, parse + layout +
page write 4,607 ms, `book.bin` 4 ms.

The ranking nobody would have guessed: **the layout engine was not the
bottleneck — writing the result out was, by 20:1.** `Page::serialize` wrote
every field with its own `HalFile::write` call: 3 pods + arena + one
`writeString` per word for the ruby text + 14 style pods per line, 2 pods per
`PageLine`, 1 tag per element. That is 398 storage calls per page, 2.3 million
for one spine.

`lib/Serialization/BufferedFile.h` already existed for exactly this problem —
its header comment records `BookMetadataCache::buildBookBin` measured at 31 s
for 200 KB before it was buffered — and the section page stream had never been
routed through it.

## What changed

### 1. Buffer the section page stream

`serialize()` on `Page`, `PageLine`, `PageImage`, `PageRotatedText`,
`PageVerticalRule`, `PageHorizontalRule`, `TextBlock` and `ImageBlock` now take
a `serialization::BufferedFileWriter&` instead of a `HalFile&`
(`lib/Epub/Epub/Page.h:32`, `Page.cpp:27`/`:64`/`:94`/`:133`/`:171`/`:223`,
`blocks/TextBlock.cpp:355`, `blocks/ImageBlock.cpp:431`). The writer lives in
`Section::BuildContext` for the whole build (`Section.h:50`, created at
`Section.cpp:423`), the page LUT records `pageWriter->position()` rather than
`file.position()` (`Section.cpp:141`), and the four per-page tables written at
commit go through their own writer (`Section.cpp:647`).

Two places touch `file` directly while a build is live and must flush first —
both do: `loadPageDuringBuild` before it seeks back to read an already-written
page (`Section.cpp:845`), and `commitBuildFile` before it positions the tables
and again before it seeks backwards to patch the header (`Section.cpp:631`,
`:658`). Buffer is 1 KB, not `BookMetadataCache`'s 4 KB: this one is held for
the whole build rather than a single streaming pass, and 1 KB already collapses
the per-page call count to a handful.

| | Storage write calls | Host wall time |
|---|---|---|
| `measure.epub` ch.0, 246 pages — before | 98,272 (400/page) | 207-295 ms |
| `measure.epub` ch.0, 246 pages — after | **325** (1.3/page) | **15-18 ms** |
| `giant.epub`, 5,816 pages — before | 2,318,426 | 4,607 ms |
| `giant.epub`, 5,816 pages — after | **7,663** | **424 ms** |

**302x fewer storage calls per page.** That factor is what transfers to the
device; the wall-clock factor is host-inflated.

Proof of identity: `BufferedFileWriter` documents capacity 0 as unbuffered
passthrough, which reproduces the old call sequence exactly. Building the same
spine with the constant at 0 and at 1024 gives `cmp`-identical `.bin` files.
Verified again after each of the two changes below.

### 2. Byte pre-check before the CJK break scan

`cjkCharacterBreakByteOffsets()` ran on **every word of every book**
(`ParsedText.cpp:524`). Before deciding the word has no CJK in it, it asked
`ESP.getMaxAllocHeap()`, reserved a vector sized to the word, and decoded the
whole word; `containsCjkBreakableCodepoint()` then decoded it a second time.

The lowest breakable codepoint is U+1100, whose UTF-8 lead byte is 0xE1, and
every 2-byte sequence and continuation byte is below that. So a word with no
byte >= 0xE1 provably contains nothing `utf8IsCjkBreakable()` answers true for.
`mayContainCjkBreakableBytes()` (`ParsedText.cpp:52`, modelled on the existing
`mayContainRtlBytes` two functions above it) guards both entry points
(`ParsedText.cpp:191`, `:171`). It is a necessary condition, not a sufficient
one — Ethiopic still takes the full scan and still comes back empty.

`giant.epub`: 424 → **330 ms** (22%). `.bin` byte-identical.

**This one is bigger on device than the host can show.** `ESP.getMaxAllocHeap()`
is `heap_caps_get_largest_free_block` on ESP-IDF — a free-list walk under the
heap lock — and it was being called once per word. The simulator returns a
constant (`crosspoint-simulator/src/Arduino.h:61`), so a host profile prices it
at zero.

### 3. ASCII shortcut for the kern-class lookup

After the write fix, `SdCardFont::getMeasureKern` was the largest CPU item at
28% of active build time. It runs two `lower_bound`s over the font's
codepoint→class tables (~80-96 entries each, ~7 comparisons) for **every
adjacent character pair the layout measures** — ~2.5 M pairs on a novel, reached
from `calculateWordWidths` → `getTextAdvanceX`.

`PerStyle::kernClassAscii` (`SdCardFont.h:204`) is a 256-byte heap block — 128
left classes then 128 right — filled from those same tables the moment they load
(`SdCardFont.cpp:309`) and freed with them (`SdCardFont.cpp:155`).
`getMeasureKern` indexes it for codepoints below 128 and falls back to the
search otherwise (`SdCardFont.cpp:650`). It is a memoization of an exact
function, so it cannot change any answer; `nullptr` (allocation failed, or the
font carries no kern data) is the unchanged slow path.

`giant.epub`: 330 → **267 ms** (19%). `.bin` byte-identical.

### Cumulative

| Step | `giant.epub` build | vs. baseline |
|---|---|---|
| baseline | 4,607 ms | 1.0x |
| + buffered page stream | 424 ms | 10.9x |
| + CJK byte pre-check | 330 ms | 14.0x |
| + ASCII kern shortcut | **267 ms** | **17.2x** |

`measure.epub` chapter (246 pages): ~250 ms → **16 ms**.

### Device weighting

The X3 is a single-core ESP32-C3 at 160 MHz with the SD card as the slow part,
so the host's 17.2x will not be 17.2x on hardware. What each fix is worth there:

* **Fix 1** — the transferable figure is 398 → 1.3 storage calls per page. On
  device each call is a recursive-mutex acquire plus SdFat bookkeeping, and each
  buffer boundary is a transaction against the volume's single shared 512-byte
  sector cache, which the interleaved 1 KB HTML reads
  (`ChapterHtmlSlimParser.cpp:26`) keep evicting. It also turns the page stream
  into sequential 1 KB transfers, which is the difference between a card's
  streaming rate and its random-write rate.
* **Fix 2** — larger on device than measured here, per the heap-lock note above.
* **Fix 3** — pure CPU, scales with the clock ratio, so its device share is at
  least the 19% measured.

The floor this cannot go below: the section file is **3.1x the size of the
chapter HTML** (7.84 MB of `.bin` for 2.56 MB of XHTML). On a slow card that
volume is the remaining cost of indexing. See item 2 of the next section.

## Instrumentation added

`serialization::BufferedFileWriter::writeCalls()` (`BufferedFile.h:58`) and one
line at build finalize (`Section.cpp:749`):

```
[SCT] Build wrote 5816 pages in 7663 storage writes
```

Storage **calls**, not bytes, because that is the number that decides the cost
on hardware — the byte count was never the problem. `LOG_DBG`, so it is
compiled out of `gh_release` (`LOG_LEVEL=1`) and free when off.

## Ranked list of what remains — measured, not fixed

1. **Update Library re-hashes the whole library on every run.**
   `LibraryUpdater::syncBook` (`src/network/LibraryUpdater.cpp:350`) takes the
   `CHECK_SHA` verdict whenever a book exists with a matching size
   (`src/network/LibrarySyncPlan.h:27`) and then calls `computeCardSha256`
   (`:321`, from `:364`), which reads the entire file off the card in
   `SHA_CHUNK` blocks to produce a digest it discards. Nothing memoizes it. The
   steady-state "nothing to do" run therefore reads the whole library from SD —
   the more up to date the card is, the more it costs. Fix: a digest sidecar
   keyed on (path, size, mtime). **Not done here**: it is a correctness-bearing
   integrity check, and the sync path cannot be exercised headlessly in this
   simulator, so it would ship unverified.
2. **A 4-byte empty ruby string per word, in every book.**
   `TextBlock::serialize` (`blocks/TextBlock.cpp:374`) writes a `writeString`
   for each word's ruby text; `rubyTexts` is empty for every non-ruby block
   (the constructor drops it, `TextBlock.cpp:50`), so that is a 4-byte length
   and nothing else, per word, forever. ≈1.0 MB of `giant.epub`'s 7.84 MB
   section file — **13% of the bytes written during indexing and read on every
   page turn.** Fix: one presence byte per block. **Not done here**: it is a
   serialization format change requiring `SECTION_FILE_VERSION` 44 → 45, and
   13% is the wrong risk/benefit to take on the same day as a 17x change and
   two other cache bumps.

   **DONE, later the same day** (owner ruling: "take it"). A presence byte per
   block plus a sparse index-prefixed list -- cheaper than the presence byte
   alone, because even a ruby line annotates only its group leaders.
   `SECTION_FILE_VERSION` 45, measured at 12.6% on `giant.epub` and 12.7% on
   `measure.epub`, with the ruby rendering proved pixel-identical across the
   change. Write-up:
   [book-notes-and-sparse-ruby-2026-08-23.md](book-notes-and-sparse-ruby-2026-08-23.md).
3. **Page turn on a cached section: 3 opens of the same `.bin` + ~11 seeks.**
   `loadPageAt` (`Section.cpp:858`) opens, re-reads `lutOffset` from the header,
   seeks three times; `saveProgress` (`EpubReaderActivity.cpp:1465`) then calls
   `getParagraphIndexForPage` (`Section.cpp:1013`) and
   `getFirstWordAnchorForPage` (`:1084`), each of which opens the same file and
   re-reads the same header again; `ProgressFile::writeAtomic`
   (`ProgressFile.h:32`) costs ~4 FAT operations for 12 bytes; the idle prewarm
   (`EpubReaderActivity.cpp:283`) adds a 4th open 400 ms later. Host cost is
   1-3 ms per turn (measured over 20 turns), and the host cannot show the SD
   cost. **Not changed**: an e-ink FAST refresh is ~600 ms, so three file opens
   are not what the reader feels, and a cached read handle on `Section` has to
   be invalidated against `commitBuildFile`'s remove+rename — real risk for a
   saving that is invisible next to the panel.
4. **A partial always rebuilds from byte 0.** `Section::startBuild`
   (`Section.cpp:343`) re-parses the whole chapter to extend a suspended
   partial, so crossing the watermark re-lays out the entire prefix. Now 17x
   cheaper, which is most of the answer. A resume-from-watermark would need the
   parser to be seekable, and expat is not.
5. **Soft-flush re-layout.** `ChapterHtmlSlimParser.cpp:1994` re-runs
   `layoutAndExtractLines` over the block remainder once a block passes
   `TEXT_BLOCK_SOFT_FLUSH_WORDS` — 750 words, or **320 with embedded CSS on**
   (`:33`, `:37`), so it is 2.3x more frequent on a styled book. Each re-entry
   re-measures every remaining word and re-runs the break DP. Bounded by the
   threshold rather than quadratic in the chapter, and after the three fixes
   `layoutAndExtractLines` and everything under it is ~40% of a much smaller
   total. Not isolated further.
6. **Home redraw opens the cover BMP for its header on every redraw.**
   `BaseTheme::drawRecentBookCover` (`src/components/themes/BaseTheme.cpp:455`)
   opens the file and calls `parseHeaders()` purely to get width/height for the
   aspect ratio, ungated — while the decode itself is correctly gated behind
   `!coverRendered` (`:499`) and snapshotted into RAM. So the decode happens
   once and a file open happens on every cursor move. Fix: cache `imgWidth`/
   `imgHeight` next to the existing `coverRectW/H`.
7. **Font picker renders its preview specimen twice per redraw** when
   antialiasing is on — `renderPreviewSpecimen` at
   `src/activities/settings/FontSelectionActivity.cpp:452` (via `renderPreviewPane`)
   and again inside `ReaderUtils::renderAntiAliased` at `:684`. CPU, not SD, and intentional
   (BW base + gray plane). Moving the cursor does **not** load a font: the list
   is built from the in-RAM registry and only the applied family is resident.
8. **Cold boot** does 3 full JSON parses (`src/main.cpp:822`-`:824`:
   settings, app state, recent books) and 3-4 full JSON writes (`:910`, `:984`,
   `EpubReaderActivity.cpp:182`, `:183`) before the first page. Small
   individually, but this is the one path where they are all serialized.

## Negative results — measured, not worth touching

* **`book.bin` (the spine/TOC/CSS index):** **4 ms** for a 24-chapter book,
  against a pre-fix chapter build of ~250 ms — 1.6% of the cold open. It already
  streams through `BufferedFileWriter`. This is the pass the word "indexing"
  most obviously points at, and it is not the problem; the absolute figure is
  what matters, since after the fixes it is a larger share of a much smaller
  total and still only 4 ms.
* **`utf8ComposeNfc` returning a copy per word** (`ParsedText.cpp:442`): the
  short-string optimization covers words up to 22 bytes, so there is no
  allocation for real text; ~1% of build CPU. Left alone.
* **`LOG_DBG("SCT", "Page %d processed")` per page:** 424 → 401 ms with it
  removed, 5% of the post-fix host build, and compiled out entirely in
  `gh_release`. Left in.
* **CSS `resolveStyle` is not linear over rules** (`css/CssParser.cpp:707`):
  `unordered_map` with a transparent hash, 2×classCount+1 lookups per element,
  no allocation. It does call `ESP.getFreeHeap()` per element (`:709`) — a
  device-only cost the host prices at zero, same class as the per-word one
  fixed above, but per element rather than per word and therefore ~6x rarer.
  Left alone.
* **Hyphenation reads nothing from SD.** The Liang trie is in flash
  (`hyphenation/generated/hyph-en.trie.h`) with fixed stack buffers. 1.6% of
  build CPU.
* **Images do not decode during a build.** The parser probes dimensions from an
  early-aborted inflate of the first ~1 KB (`ChapterHtmlSlimParser.cpp:1177`);
  full extraction is the fallback for a failed header probe only (`:1181`).
* **Glyph metrics do not touch SD during layout, after the first paragraph.**
  The 768-entry-per-style advance table survives `clearCache()` and every
  section (`SdCardFont.cpp:1313`-`:1320`), so a Latin book's whole indexing run
  is SD-free for metrics.
* **Browse Files / Manage Files do not stat per file**
  (`FileBrowserActivity.cpp:39`, `FileManagerActivity.cpp:91`) — name plus the
  cached FAT directory attribute only. Not a suspect.
* **Font discovery at boot never opens a font file** —
  `SdCardFontRegistry::discover` reads directory entries and parses filenames
  (`lib/EpdFont/SdCardFontRegistry.cpp:112`, `:209`). 2 + one open per family
  directory.
